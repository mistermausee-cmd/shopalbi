## 1. Что это и зачем

Веб-инструмент под одну конкретную схему заработка в Albion Online:

> купить экипировку в королевском городе → отвезти в Карлеон → продать NPC
> «Чёрный рынок» (далее **ЧР**)

Отвечает на три вопроса цифрами:

1. **Что везти прямо сейчас** и сколько это даст в серебре и процентах.
2. **Из какого города** базироваться.
3. **На заданный бюджет** — какой список закупки и **сколько штук реально можно
   купить** (не «сколько влезает по деньгам», а сколько физически есть на рынке).

Плюс две вспомогательные вкладки: таблица средних цен по всем городам и «Мои
сеты» — где дешевле всего купить свой боевой/рабочий комплект целиком.

**Сервер: Europe. Аккаунт: с Premium** (влияет на налог — 4% вместо 8%).

Игру запускать не нужно, инструмент читает только публичные данные.

## 2. Окружение и обновление (читать перед любым деплоем)

### 2.1 Машина

| | |
|---|---|
| Хостинг | Azure |
| ОС | Ubuntu 24.04 |
| Ресурсы | **4 vCPU / 16 ГБ RAM** |
| Работа под | `root` |
| Каталог репозитория | `~/shopalbi` |
| Порт | `8000` |
| Логи на хосте | `/root/logs/shopalbi.log` (ротация 5 МБ × 3) |
| Данные | named volume `shopalbi-data`, внутри контейнера `/data` |

Дефолты в `docker-compose.yml` рассчитаны именно на 4 vCPU / 16 ГБ (90 дней
истории, кеш SQLite 1 ГБ, обновление цен каждые 5 минут). Для слабой машины см.
§10.2.

### 2.2 Команда обновления — давать её в КАЖДОМ ответе, где менялся код

Пока PR #3 не смержен (берём ветку):

```bash
cd ~/shopalbi && \
git fetch --all --prune && \
git checkout -B v5 origin/feat/v5-audit-and-rebuild && \
sudo docker compose up -d --build && \
echo '--- ждём старт ---' && sleep 40 && \
curl -s localhost:8000/api/health && echo && \
sudo tail -n 25 /root/logs/shopalbi.log
```

После мержа в `main`:

```bash
cd ~/shopalbi && \
git fetch --all --prune && \
git checkout -B main origin/main && \
sudo docker compose up -d --build && \
echo '--- ждём старт ---' && sleep 40 && \
curl -s localhost:8000/api/health && echo
```

Ожидаемый ответ: `{"status":"ok","version":"5.3.0"}` — **и в ответе пользователю
всегда указывать, какую версию он должен увидеть**, потому что по внешнему виду
сайта определить, поднялся ли новый код, невозможно.

### 2.3 Обязательные требования к команде обновления

Это не стилистика, каждое правило появилось из конкретной поломки.

1. **`git fetch` + `git checkout -B <ветка> origin/<ветка>`, а НЕ `git pull`.**
   Реальный случай: рабочее дерево стояло на ветке фичи, `git pull` ответил
   «Already up to date», `docker build` вышел полностью `CACHED`, старый фронтенд
   продолжил работать — и это выглядело как вечная загрузка интерфейса. Полдня
   ушло на поиск «бага», которого не было.
2. **Проверка версии в конце.** Всегда `curl -s localhost:8000/api/health`, и в
   тексте ответа — «ждём версию X, если другая — код не поднялся».
3. **Не предлагать `docker compose down`/`stop`.** `up -d --build` пересоздаёт
   контейнер сам. Пользователь про это спрашивал — стоит сказать явно.
4. **Одна строка через `&&`**, чтобы копипастить целиком.
5. **`cd ~/shopalbi` в начале.** Без этого `docker compose` отвечает
   `no configuration file provided: not found` — уже наступали.

### 2.4 Проблема «два сайта одновременно» и как её исключить

Симптом: открываешь сайт и видишь то новую версию, то старую; цифры «прыгают»;
после обновления часть страниц старая. Причина — **больше одного контейнера
обслуживает порт**, либо остался контейнер от другого compose-проекта (имя
проекта берётся из имени каталога, поэтому копия репозитория в другой папке
создаёт второй независимый стек).

Диагностика:

```bash
# 1. Что вообще запущено
sudo docker ps -a --format 'table {{.Names}}\t{{.Image}}\t{{.Status}}\t{{.Ports}}'

# 2. Кто держит порт 8000
sudo ss -tlnp | grep :8000

# 3. Какие compose-проекты есть на машине
sudo docker compose ls -a

# 4. Нет ли второй копии репозитория
ls -d ~/shopalbi* /root/shopalbi* /opt/shopalbi* 2>/dev/null
```

Здоровое состояние: **ровно один** контейнер с именем `shopalbi`, один
слушатель на `:8000`, один compose-проект.

Если контейнеров несколько:

```bash
# аккуратно: гасим лишние по имени, свой стек не трогаем
sudo docker rm -f <имя_лишнего_контейнера>

# либо погасить чужой compose-проект целиком
sudo docker compose -p <имя_проекта> down
```

Проверить, что версия одна и та же с разных сторон:

```bash
curl -s localhost:8000/api/health          # что отвечает локально
curl -s localhost:8000/ | grep -o 'v[0-9]\+\.[0-9]\+\.[0-9]\+' | head -1
```

Если в браузере всё равно старое, а `curl` показывает новое — это кеш браузера,
но он **не должен** так себя вести: `index.html` отдаётся с
`Cache-Control: no-cache`, а `app.js`/`styles.css` запрашиваются с `?v=<версия>`.
Если старое всё же липнет, значит либо контейнер не тот, либо перед ним стоит
кеширующий прокси.

### 2.5 Что происходит с данными при обновлении

- `shopalbi-data` (volume) переживает пересборку — сохраняются история цен,
  живой стакан и **сеты пользователя**.
- Миграции схемы применяются автоматически при старте (§6.4).
- Производные таблицы (`agg`, `bm_offer`) при необходимости пересобираются на
  старте из уже имеющихся данных, поэтому сайт работает **сразу**, а не пустой
  первые две минуты.
- Первый рефреш истории после старта ~2 минуты (90 дней), индикатор наверху
  жёлтый. Это норма.

### 2.6 Команды обслуживания

Абсолютный путь обязателен: рабочая папка в контейнере `/app/backend`, а скрипты
лежат в `/app/scripts`.

```bash
# самопроверка расчётов
cd ~/shopalbi && sudo docker compose exec shopalbi python /app/scripts/audit.py --window week --top 10

# компактный снимок БД для разбора (≈16 МБ, кладётся в /root/logs)
cd ~/shopalbi && sudo docker compose exec shopalbi python /app/scripts/export_snapshot.py --out /logs

# логи
sudo docker compose logs -f
sudo tail -f /root/logs/shopalbi.log
grep "order feed" /root/logs/shopalbi.log | tail -3   # здоровье живого стакана
```

**Прежде чем писать в ответ любую команду `docker compose exec ...` — проверить
её в собранном образе.** Один раз забыли `COPY scripts/` в `Dockerfile` и выдали
неработающую инструкцию.

## 3. Что показывает интерфейс

Пять вкладок, все на одной странице (`frontend/index.html`), переключение без
перезагрузки. Наверху — общая панель фильтров: окно агрегации, тир, качество,
город закупки, бюджет, режимы покупки/продажи.

### 3.1 🔥 Выгодные флипы

Основная таблица. Строка = «предмет + качество + город закупки». Колонки:

| Колонка | Смысл |
|---|---|
| Предмет / Тир / Качество | что покупать; тир в формате `T7.2` |
| Город | где дешевле всего купить |
| Цена закупки | `sell_price_min` в этом городе (сколько отдашь за штуку) |
| Ставка ЧР | ставка выкупа NPC ЧР — **это текущая ставка ордера, не средняя** |
| Прибыль / % | чистыми за штуку после налога |
| EV / EV % | то же с поправкой на риск гибели в дороге (§7.4) |
| ЧР/шт в день | сколько штук в день реально уходит на ЧР (из истории сделок) |
| Выкупят за | оценка времени, за которое рынок впитает объём (`est_absorb_h`) |
| Доступно | сколько штук физически стоит в продаже в городе (живой стакан) |
| Надёжность | 0–100, насколько можно доверять этой оценке (§7.5) |
| Оценка | сводный балл возможности |

### 3.2 🧮 План закупки

Вводишь бюджет — получаешь список закупки **по каждому городу**, с итогом и
рангом городов. Ключевое отличие от «просто топ флипов»: план ограничен
**реальной глубиной рынка**. Если T8-шлема в Лимхурсте лежит 3 штуки, план
поставит 3, а не «бюджет / цена».

Ограничители (все настраиваемые, §10):
- глубина живого стакана с уценкой по возрасту (§7.6);
- если стакана нет — заглушка `RECOMMEND_NODEPTH_CAP` (60 шт);
- не более `RECOMMEND_VOLUME_CAPTURE` (15%) суточного оборота ЧР по позиции —
  иначе ты сам обрушишь ставку;
- не более `RECOMMEND_MAX_ITEM_SHARE` (30%) бюджета в одну позицию;
- не более `RECOMMEND_MAX_ITEMS` (80) строк.

### 3.3 🏙 Города закупки

Ранжирование городов: суммарный потенциал прибыли, число позиций, средний
процент, риск дороги. Отвечает на вопрос «где базироваться».

### 3.4 📊 Средние цены

Таблица средних цен по всем городам за выбранное окно, включая Brecilien
(справочно — как источник закупки он исключён, §10). Тут же VWAP и объёмы.

### 3.5 🎒 Мои сеты

Пользователь собирает свой комплект (броня, оружие, маунт, зелья, еда, удочки,
роба рыбака — каталог 8114 предметов), сохраняет на сервере, и получает **город,
где весь комплект обойдётся дешевле всего**.

Особенности:
- **Города с полным сетом ранжируются выше дешёвых с недостачей.** Город, где
  нет одной вещи, означает вторую поездку — это дороже любой экономии.
- **Эквивалент по силе предмета** (§7.7): T8.0 = T7.1 = T6.2 = T5.3 = T4.4, и
  система подбирает самый дешёвый вариант равной силы.
- Цены тянутся **по требованию** при расчёте сета, а не для всех 8114 предметов.

### 3.6 Комбинированный отбор (работает на ВСЕХ вкладках, кроме сетов)

Клик по заголовку колонки добавляет её в набор критериев, повторный клик —
убирает. Активные критерии подсвечены. Строки ранжируются по **сумме
перцентильных позиций** по всем выбранным критериям.

Почему перцентили, а не min-max: распределения крайне скошены — одна позиция с
прибылью 500k рядом с тысячами по 2k. При min-max всё, кроме выброса,
схлопывается в ~0 и отбор перестаёт различать строки. Перцентиль устойчив к
выбросам. Доступно 13 критериев (`RANK_KEYS` в `engine.py`), у каждого объявлено
направление «лучше» — например, `absorb` и `buy_price` лучше меньше.

## 4. Источники данных

Два независимых канала. Оба нужны: REST даёт историю и покрытие, NATS — точность
«прямо сейчас».

### 4.1 REST: Albion Online Data Project (AODP)

Хост EU: `https://europe.albion-online-data.com`.

| Эндпоинт | Что даёт |
|---|---|
| `/api/v2/stats/prices/{ids}` | текущие лучшие цены: `sell_price_min`, `buy_price_max`, метки времени |
| `/api/v2/stats/history/{ids}` | история сделок: цены и количества по бакетам |

Проверенные факты:

- **Лимиты**: 180 запросов/мин и 300/5 мин. Стоит `RATE_PER_MIN = 165`. Полный
  рефреш цен — примерно **40 запросов**, то есть ~8.2 запроса/мин из 180. Лимит
  API **никогда не является узким местом**, узкое место — диск на таблице
  `history`.
- **Лимит URL** 4096 символов, батчи собираются под `MAX_URL_LEN = 3900`.
- **Глубина истории: 180 дней доступно.** Берём 90 (`HISTORY_DAYS`).
- **`time-scale=1` (часовые бакеты) отстаёт** от суточных — данные приходят
  разреженно и с задержкой. Используем `time-scale=24`.
- Данные — краудсорсинг с клиентов игроков. Есть города/предметы с дырами и
  устаревшими метками. Отсюда весь блок проверок свежести и котировок (§7.8).

### 4.2 NATS: живой поток ордеров

Публичный поток AODP. Даёт то, чего нет в REST: **глубину стакана** — сколько
штук стоит по какой цене.

Проверенные факты (это самое «дорого добытое» знание в проекте):

- **Подписываться ТОЛЬКО на `marketorders.deduped`.** Замер на 465
  идентификаторах: тема `.bulk` пересекается с `.deduped` **на 100%**. Подписка
  на обе давала **двойной счёт** объёмов.
- **В `.deduped` цены НЕ умножены**, а в `ingest`-темах цены **×10000**. Смешать
  темы = ошибка в цене на 4 порядка.
- **`LocationId` приходит числом** (int), не строкой.
- **`3003` = Black Market, `3005` = Caerleon.** Подтверждено и по REST, и по
  NATS. В коде раньше было наоборот — это был баг №1 из четырёх критичных.
- **NPC-ордера ЧР имеют `Expires` в году 3025.** Порог `NPC_EXPIRY_YEAR = 2100`
  отделяет их от игровых. Без этого NPC-ставка попадала в расчёт конкуренции.

Запись пачками: буфер сбрасывается каждые `ORDER_FLUSH_SECONDS` (3 с) или по
`ORDER_FLUSH_MAX` (2000) записей.

### 4.3 Каталог предметов

`https://raw.githubusercontent.com/ao-data/ao-bin-dumps/master/formatted/items.json`,
кешируется на `CATALOG_MAX_AGE_DAYS` (7 дней). Русские названия — `LANG = RU-RU`.

Строятся два набора:
- `items` — только то, что покупает ЧР: T4–T8 боевая экипировка, слоты
  `MAIN/2H/OFF/HEAD/ARMOR/SHOES/CAPE/CAPEITEM/BAG`;
- `shop_items` — всё для вкладки сетов (8114 записей), включая маунтов, еду,
  зелья, инструменты.

Проверено эмпирически: **сумки и фракционные плащи ЧР выкупает** (проверено на
T5 FW-плаще), а **рюкзаки собирателя и `*_GATHERER_*` — нет**: `buy = 0` и
нулевая история сделок. Логично — мобы не дропают снаряжение для собирательства,
а ЧР симулирует дроп с мобов. Отсюда `EXCLUDE_ID_TOKENS`.

## 5. Архитектура и карта файлов

Поток данных:

```
AODP REST ──┐
            ├─→ storage.py (SQLite) ─→ engine.py (расчёты) ─→ main.py (API) ─→ frontend
NATS      ──┘         ↑                      ↑
ao-bin-dumps ─→ catalog.py            shopsets.py (вкладка сетов)
                                      scheduler.py (периодика)
```

### 5.1 Бэкенд, `backend/app/`

| Файл | Строк | Назначение |
|---|---|---|
| `config.py` | 406 | **Единственный** источник констант и env-переменных. Игровые константы с комментариями-источниками. `net_factor()` / `cost_factor()`. |
| `engine.py` | 1268 | Все расчёты: формулы оценок, `Analytics` (flips, plan, city_ranking, stats_table), комбинированное ранжирование. |
| `storage.py` | 844 | SQLite: схема, миграции, upsert'ы, **агрегация в SQL**, выборки `flip_rows`/`stats_rows`, живой стакан. |
| `main.py` | 521 | FastAPI: 20 эндпоинтов, валидация входа, Basic Auth, раздача фронтенда. |
| `shopsets.py` | 315 | Вкладка сетов: `item_power`, `item_family`, `equivalent_ids`, `SetPricer`. |
| `catalog.py` | 274 | Загрузка/парсинг каталога, фильтры слотов, чистка названий, `tier_label`. |
| `nats_consumer.py` | 232 | Поток ордеров, отсечение NPC, батч-запись. |
| `aodp_client.py` | 165 | HTTP-клиент: rate limiter, батчи по длине URL, ретраи. |
| `scheduler.py` | 114 | APScheduler: рефреш цен (5 мин), истории (4 ч), пересборка производных. |

### 5.2 Фронтенд, `frontend/`

| Файл | Строк | Назначение |
|---|---|---|
| `app.js` | 1286 | Вся логика UI: вкладки, фильтры, комбинированный отбор, редактор сетов, рендер таблиц. Без фреймворков. |
| `styles.css` | 413 | Тёмная тема, адаптив. |
| `index.html` | 211 | Разметка, панель фильтров, контейнеры вкладок. |

### 5.3 Скрипты, `scripts/`

| Файл | Строк | Назначение |

### 6.3 Порядок инициализации — НЕ МЕНЯТЬ

**Таблицы → миграции колонок → индексы.** Именно в этом порядке
(`Storage.__init__`). Причина: индекс по колонке, которой в старой БД ещё нет,
падает и обрывает весь апгрейд. Один раз так и случилось — обновление на живой
базе разваливалось.

### 6.4 Миграции и эпоха данных

`_MIGRATIONS` — список `(таблица, колонка, ALTER)`, применяется идемпотентно:

```python
("items",      "name_disp", "ALTER TABLE items ADD COLUMN name_disp ...")
("items",      "name_norm", "ALTER TABLE items ADD COLUMN name_norm ...")
("order_book", "npc",       "ALTER TABLE order_book ADD COLUMN npc ...")
```

`DATA_EPOCH = 2` — счётчик «смысл данных изменился». При росте эпохи
принудительно очищаются `_EPOCH_PURGE = ["order_book", "agg", "bm_offer"]`.
Нужно потому, что после исправления бага с двойным счётом NATS-тем и
перепутанных ID локаций **уже накопленные** данные были неверны, а схема при этом
не менялась — обычные миграции такое не лечат.

**Правило: если меняешь смысл содержимого производных таблиц — увеличивай
`DATA_EPOCH`.** Иначе пользователь получит смесь старых неверных и новых верных
чисел, что хуже, чем просто неверные.

`_KNOWN_TABLES` — allow-list: единственное место, где имя таблицы попадает в SQL
строкой, защищено списком разрешённых.

### 6.5 Свёртка `agg` — как считается окно

Окна: `day`=1, `3d`=3, `week`=7, `month`=30, `quarter`=90 дней.

Окно покрывает последние N **полных** UTC-суток и **исключает сегодняшний
неполный бакет**:

```
first = today - N дней
last  = today - 1 день
WHERE day >= first AND day <= last
```

Это был баг №4 из четырёх критичных: старый код брал `day >= today - N`, то есть
захватывал **N+1** бакет (включая неполный сегодняшний) и делил на N — суточные
объёмы получались завышенными.

VWAP считается взвешенным по количеству:
`SUM(avg_price * item_count) / SUM(item_count)`, при нулевом объёме — простое
`AVG(avg_price)`.

В `meta` пишется `agg_range_<window>` = `"YYYY-MM-DD..YYYY-MM-DD"` — точный
покрытый диапазон. Нужно, потому что `agg` — снимок, пересобираемый раз в
`HISTORY_REFRESH_HOURS`, и вскоре после UTC-полуночи он ещё описывает вчерашний
диапазон. Честнее показать реальные даты, чем писать «последние N дней».

### 6.6 Зачем агрегация в SQL

Прошлая версия тянула ~887k строк истории и ~274k строк цен в словари Python на
**каждый запрос**, а планировщик бюджета — ещё и по разу на каждый город-кандидат.
На 6 городах это риск OOM. Сейчас — один `INSERT..SELECT..GROUP BY`, нулевой
расход памяти Python; поиск флипов — один индексированный SQL-запрос, где фильтр
по прибыли выполняется **в SQL**, и в Python попадают только выжившие строки.

## 7. Формулы — детально

Это самый важный раздел. Каждая формула здесь имеет обоснование; менять их
без перепроверки нельзя.

### 7.1 Прибыль

Множители (`config.net_factor` / `cost_factor`):

```
продажа мгновенно (в ордер выкупа ЧР):   net  = 1 − SALES_TAX          = 0.96
продажа своим ордером на ЧР:              net  = 1 − SALES_TAX − FEE    = 0.935
покупка мгновенно (из ордера продажи):    cost = 1                      (сбора нет)
покупка своим ордером:                    cost = 1 + SETUP_FEE          = 1.025
```

```
profit     = bm_bid × net − buy_price × cost
profit_pct = profit / (buy_price × cost)
```

Обоснование (wiki: Marketplace, Margin):
- **Налог на продажу** — 8%, с Premium 4%. Берётся при **завершении** сделки.
  Применяется всегда.
- **Сбор за размещение** 2.5% — берётся при **создании или изменении** ордера.
  **НЕ берётся**, когда ты мгновенно покупаешь из существующего ордера продажи и
  когда мгновенно продаёшь в существующий ордер выкупа.

Это был баг №2 из четырёх критичных: старый код вычитал сбор 2.5% и в
мгновенном сценарии, занижая прибыль каждого флипа на 2.5% выручки.

**Округление множителей до 6 знаков (`_FACTOR_DP`)** — не косметика. `1 − 0.04 −
0.025` в float даёт `0.9349999999999999`, тогда как интерфейс показывает `0.935`.
Эта невидимая щель иногда переворачивала округление, и показанную прибыль
становилось невозможно воспроизвести из показанных исходных чисел.

### 7.2 Лестница качества

Правило игры (wiki: Marketplace + Black Market): **ордер на покупку принимает
предметы своего качества ИЛИ ВЫШЕ**, и ЧР считает каждое качество отдельным
предметом — поэтому он нередко платит за низкое качество больше, чем за высокое.

Значит, продавая предмет качества Q, доступна лучшая из ставок по всем q ≤ Q:

```
bm_bid(item, Q) = MAX(buy_price_max[item, q])  для всех q ≤ Q
```

В `bm_offer` хранится и `src_quality` — по какому именно качеству ставка. Это
было баг №3 из четырёх критичных: строгое сопоставление качества теряло реальные
возможности. Замер: правило даёт **9453 строки из 15497** в `bm_offer` и **274
флипа из 488** — то есть больше половины возможностей просто не находилось.

Реализация опирается на документированную гарантию SQLite: «голые» колонки в
агрегате `MAX()`/`MIN()` берутся из той строки, которая дала экстремум.

Названия качеств (как в русском клиенте, чтобы читать прямо с экрана):
`1 Обычное, 2 Хорошее, 3 Выдающееся, 4 Отличное, 5 Шедевральное`.
Раньше показывались `q1..q5` — пользователь не мог сопоставить с игрой.

### 7.3 Оценки-компоненты (0..1)

**`liquidity_score(daily)`** — логарифмическая:
```
log1p(daily / FLOOR) / log1p(REF / FLOOR),   FLOOR = 3, REF = 400
```
Оборот ЧР охватывает **четыре порядка**: нишевый T8-оффхенд уходит единицами в
день, `T5_BAG` — около 4300. Прежний код делил на 20, из-за чего почти всё
упиралось в 1.0 и оценка не несла информации.

**`stability_score(bid, vwap)`** — согласованность ставки с историей:
```
vwap <= 0        → 0.35            (нет истории — умеренный скептицизм)
bid <= vwap      → 1.0
иначе           → 1 − (bid/vwap − 1) / (BM_MAX_VS_VWAP − 1)
```
Ставка выше VWAP — как раз опасный случай: выглядит как бесплатное серебро и
обычно исчезает, пока ты едешь.

**`competition_score(bid, ask)`** — давление чужих ордеров продажи на ЧР:
```
ask <= 0 или bid <= 0 → 1.0        (перед нами никого)
иначе                → clamp((ask − bid) / (0.10 × bid))
```
На ЧР есть и игровые `offer`-строки. Если дешёвейшая из них не выше ставки NPC,
этих продавцов обслужат раньше тебя.

**`freshness_score`** — по **слабому звену**:
```
min(1 − buy_age_h / FLIP_MAX_AGE_HOURS,  1 − bm_age_h / BM_MAX_AGE_HOURS)
```
Свежая цена в городе не спасает устаревшую ставку ЧР.

### 7.4 Риск дороги и EV

Дорога Карлеон ↔ королевские города идёт через красную зону. Модель:

```
p          = базовая частота ганка × CITY_RISK_MULTIPLIER[город]   (клип 0..0.95)
EV         = (1 − p) × выручка − затраты
```

Затраты вычитаются **полностью**, выручка — только с вероятностью выживания:
погибнув, ты теряешь и товар, и уже уплаченные деньги.

`GANK_RATE` = 0.08 по умолчанию, разумный диапазон 5–15%.
`CITY_RISK_MULTIPLIER`: Карлеон **0.0** (ЧР в том же городе, красной зоны нет),
пять королевских городов 1.0, Brecilien 1.4 (неудобный выход, и он всё равно
исключён из закупки).

Время рейса `CITY_TRIP_HOURS` + `LOAD_OVERHEAD_HOURS` (0.35 ч) — для прибыли в
час. Оценка грубая, но единообразная: задача — ранжировать города, а не
измерять секундомером.

### 7.5 Надёжность (0..100)

Взвешенная сумма пяти компонент:

| Компонента | Вес |
|---|---|
| свежесть (`fresh`) | **0.30** |
| стабильность (`stab`) | **0.25** |
| ликвидность (`liq`) | **0.22** |
| глубина (`depth`) | **0.13** |
| конкуренция (`comp`) | **0.10** |

Сумма весов = 1.0. Если по предмету нет живого стакана, `depth` считается
**нейтральной (0.5)**, а не нулём — отсутствие данных не то же самое, что плохие
данные.

### 7.6 Уценка глубины по возрасту

```
depth_trust(age):
    age <= ORDER_TRUST_FRESH_MINUTES (30)  → 1.0
    иначе линейно до ORDER_STALE_TRUST (0.5) на границе удержания
usable(amount) = max(1, int(amount × depth_trust(age)))
```

Это то, что позволяет держать окно удержания широким (покрытие) **без** того,
чтобы планировщик обещал количества, уже кем-то выкупленные (точность).
`max(1, ...)` — чтобы реальный ордер никогда не округлялся в ноль.

Окна удержания: `ORDER_MAX_AGE_MINUTES` = 720 (12 ч) для городов,
`BM_ORDER_MAX_AGE_MINUTES` = 120 (2 ч) для ЧР — ставки ЧР живут заметно меньше.

Рассматривали вариант «широкое окно без уценки» — отвергнут, он возвращает
переоценку доступного количества, ровно то, от чего уходили.

### 7.7 Эквивалент по силе предмета (вкладка сетов)

```
item_power(tier, enchant) = 300 + (tier + enchant) × 100
```

Отсюда T8.0 = T7.1 = T6.2 = T5.3 = T4.4 — одна и та же сила, разная цена.
Система подбирает **самый дешёвый вариант равной силы**.

**Защита от подмены именных артефактов.** Эквивалент требует **совпадения
отображаемого имени**, а не только семейства ID. Причина: восемь семейств
экипировки имеют «ловушку имени» — в одном семействе ID лежат разные предметы.
Например `2H_AXE` содержит «Руку Кхора»; аналогично `2H_FIRESTAFF`, `OFF_BOOK`,
`2H_QUARTERSTAFF` и другие. Без проверки имени система молча предлагала купить
артефакт вместо обычного оружия.

**Эквивалент применяется только к экипировке.** Для еды, зелий и маунтов —
отключён: зачарованная еда не «равносильна» обычной, она просто лучше, и
подменять её нельзя.

**Полнота сета важнее цены.** Города, где доступен весь сет, ранжируются выше
более дешёвых, но неполных: отсутствие одной вещи = вторая поездка.

### 7.8 Проверки котировок (защита от мусора в краудсорсе)

| Проверка | Значение | Смысл |
|---|---|---|
| `BM_MAX_VS_VWAP` | 2.2 | ставка ЧР выше 2.2 × VWAP — подозрительный выброс |
| `BM_MIN_VS_VWAP` | 0.25 | ставка ниже 0.25 × VWAP — вероятно мусор |
| `CITY_MAX_VS_VWAP` | 3.0 | цена в городе выше 3 × VWAP — не берём |
| `FLIP_MAX_AGE_HOURS` | 8.0 | предел устаревания цены в городе |
| `BM_MAX_AGE_HOURS` | 3.0 | предел устаревания ставки ЧР |
| `DROP_SPIKED_BIDS` | `False` | выбросы **не удаляются**, а понижаются в оценке |

Последнее — сознательное решение: удалять строку значит скрывать от пользователя
информацию; понижать в надёжности — показывать её с честной пометкой.

### 7.9 Комбинированное ранжирование

`RANK_KEYS` объявляет 13 критериев в виде `(поле, лучше_больше)`:

```
profit, profit_pct, ev_unit, ev_pct, opportunity, throughput,
reliability, bm_volume, available, profit_vwap, bm_trend   → лучше больше
absorb (est_absorb_h), buy_price                           → лучше меньше
```

Ранг строки = сумма **перцентильных** позиций по всем выбранным критериям.
Связки (одинаковые значения) делят средний ранг.

**Сортировка идёт по точному `rank_exact` (float), а отображается округлённый
`rank_score` (int).** Если сортировать по округлённому, на один балл приходится
около 20 строк, и порядок внутри становится случайным — при перезагрузке
страницы список «прыгает».

### 7.10 Правило воспроизводимости арифметики

**Все производные величины считаются из точных значений, но так, чтобы результат
совпадал с тем, что можно посчитать по показанным на экране числам.** Если
пользователь берёт калькулятор, подставляет цену закупки и ставку ЧР с экрана и
получает не ту прибыль, которая написана рядом — доверие к инструменту падает
полностью, независимо от того, кто «математически прав». Отсюда округление
множителей (§7.1) и явный показ всех входных величин в строке.

## 8. Механики игры, которые заложены в расчёты

### 8.1 Чёрный рынок

- NPC-торговец **в Карлеоне**. Покупает у игроков экипировку, чтобы потом
  «выдавать» её как дроп с мобов.
- Выставляет **ордера на выкуп** (`buy_price_max`) с ограниченным количеством.
- **Каждое качество — отдельный предмет** для ЧР, поэтому за низкое качество он
  порой платит больше, чем за высокое (см. лестницу качества, §7.2).
- Не покупает то, что мобы не дропают: снаряжение собирателя, рюкзаки, инструменты.
- Ставки ЧР живут **недолго** — отсюда отдельный, более жёсткий порог свежести
  (`BM_MAX_AGE_HOURS` = 3 ч) и отдельное окно удержания ордеров (2 ч).

### 8.2 Налоги и сборы

Разобрано в §7.1. Кратко: налог 4% (Premium) при завершении продажи — всегда;
сбор 2.5% — только при создании/изменении своего ордера.

### 8.3 Города

Королевских городов пять как источников закупки: **Bridgewatch, Fort Sterling,
Lymhurst, Martlock, Thetford**. Плюс Карлеон (закупка на месте, риск 0).

**Brecilien исключён из закупки** (`EXCLUDED_BUY_CITIES`). Это хаб Королевства
фей, не королевский город, и выбираться из него в сторону Карлеона медленно и
неудобно. В таблице средних цен он остаётся — справочно.

### 8.4 Дорога

Карлеон окружён красной зоной, проезд туда/обратно — риск ганка. Модель риска и
времени рейса — §7.4.

### 8.5 Обратный рейс (исследовано, в продукт НЕ включено)

Идея: не гнать порожняком из Карлеона обратно в город закупки, а везти то, что в
королевских городах дороже.

Проведён замер на живых ценах (`.probe/back.py`, `.probe/back2.py`). Модель:

```
покупаешь в Карлеоне из ордера продажи   → сбора нет
продаёшь в королевском городе:
   мгновенно в ордер выкупа  → net 0.96
   своим ордером продажи     → net 0.935
риск ганка на обратном пути тот же, что и туда
```

**Вывод по классам товара, который держится устойчиво:** осмысленный обратный
груз — это ресурсы и расходники, а не экипировка. Карлеон — единственный город с
доступом ко всем биомам красной зоны, поэтому там системно дешевле сырьё, тогда
как в каждом королевском городе дорого «чужое» для его биома сырьё (у каждого
города свой профильный ресурс, остальные три-четыре — привозные).

**Конкретные цифры прибыли здесь сознательно не приводятся: они живут часами.**
Если возвращаться к этой задаче — перезамерить скриптами `.probe/back*.py`, а не
брать числа из документа.

Что нужно для интеграции в продукт (не сделано):
1. Расширить каталог ресурсами/расходниками (в `items` их сейчас нет — там только

Общие параметры `/api/flips`, `/api/cities`, `/api/plan`:

```

sort        одно из _FLIP_KEYS
direction   asc | desc
limit       1..2000 (флипы), у stats ещё offset
rank        список критериев через запятую, например
            'profit_pct,bm_volume,absorb' — ПЕРЕКРЫВАЕТ sort
```

Неизвестный критерий в `rank` → `400` со списком допустимых. Неизвестный
`window` / `mode` / `buy_city` → `400`. Валидация `buy_city` появилась не сразу:
без неё произвольный город молча давал пустой результат вместо ошибки.

запись ордеров, гонки за SQLite. Если понадобится масштабирование — выносить
планировщик и потребителя в отдельный процесс, а не поднимать воркеры.

## 11. Как проверять, что расчёты верны

### 11.1 `scripts/audit.py` — независимая перепроверка

Главный инструмент доверия. Скрипт **не переиспользует** код движка: он берёт
сырые строки из БД, считает прибыль своей отдельной реализацией и сравнивает с
тем, что отдаёт API. Расхождение = баг в одном из двух, и это видно сразу.

```bash
cd ~/shopalbi && sudo docker compose exec shopalbi python /app/scripts/audit.py --window week --top 10
```

Что проверяет: арифметику прибыли, применение лестницы качества, границы окна
агрегации, согласованность `agg` с `history`, санитарные проверки котировок.

**Если меняешь формулу — обнови `audit.py` отдельной реализацией, а не копией
кода движка.** Копия проверяет только то, что копирование прошло без опечаток.

### 11.2 `scripts/export_snapshot.py`

Компактный дамп БД (~16 МБ) для разбора вне сервера:

```bash
cd ~/shopalbi && sudo docker compose exec shopalbi python /app/scripts/export_snapshot.py --out /logs
```

Пользователь этим уже пользовался — выкладывал дамп в ветку `logs` репозитория,
чтобы можно было разобрать расчёты на реальных данных. Это рабочий канал, если
понадобятся живые данные: **попросить дамп, а не догадываться**.

### 11.3 Тестовое окружение в сессии

`/projects/sandbox/.probe/` — набор проверочных скриптов, накопленных за работу.
Сохранились: `full.py` (сплошная проверка инвариантов, 31 КБ), `t1.py`–`t5.py`,
`back.py`/`back2.py` (обратный рейс), `nt.py`/`nt2.py`/`topics.py` (проверка
NATS-тем), `ui2.sh`/`shot.sh`/`dbg.sh` (браузерные проверки), `full.out`
(результат последнего прогона).

**Живая тестовая БД `/projects/sandbox/.probe/full/shopalbi.db` НЕ сохраняется
между сессиями** — окружение сбрасывается. Если нужна — пересобрать рефрешем или
попросить дамп у пользователя (§11.2).

Запуск (нужен Python 3.12; на 3.9 FastAPI падает на аннотациях `int | None`):

```bash
SHOPALBI_DATA_DIR=/projects/sandbox/.probe/full \
  /projects/sandbox/.venv312/bin/python /projects/sandbox/.probe/full.py
```

cd /projects/sandbox/shopalbi

### 11.5 Особенности среды разработки (важно для планирования работы)

- **Фоновые процессы не выживают между вызовами bash.** Поднять сервер в одном
  вызове и обратиться к нему в следующем **нельзя**. Всё, что требует живого
  сервера, — запускать и проверять **в одном** вызове (старт, `sleep`, `curl`,
  убийство процесса).
- `/tmp` очищается между вызовами. Артефакты складывать в `/projects/sandbox/`.
- Таймаут `timeout` — до 1800000 мс (30 мин).

### 11.6 Масштаб последней сплошной проверки

v5.1.2: проверено **2111 инвариантов** — согласованность агрегатов, границы окон,
лестница качества, арифметика прибыли на каждой строке, поведение API на
граничных параметрах, воспроизводимость чисел с экрана. Нашлось 4 реальных

## 13. Грабли — читать перед любым изменением

Каждый пункт — реально допущенная ошибка. Не повторять.

### 13.1 Данные и игровые правила

1. **`3003` = Black Market, `3005` = Caerleon.** Было перепутано. Проверено и по
   REST, и по NATS. Не «поправлять по памяти».
2. **Сбор 2.5% не берётся при мгновенной сделке.** Занижало прибыль каждого флипа.
3. **Ордер выкупа принимает своё качество и ВЫШЕ.** Строгое сопоставление
   качества теряло больше половины возможностей.
4. **Окно агрегации — последние N ПОЛНЫХ суток, без сегодняшнего бакета.**
   `day >= today - N` захватывает N+1 бакет и завышает суточные объёмы.
5. **Подписка только на `marketorders.deduped`.** `.bulk` пересекается на 100%,
   подписка на обе = двойной счёт.
6. **В `ingest`-темах цены ×10000, в `.deduped` — нет.** Смешение = ошибка на 4
   порядка.
7. **NPC-ордера ЧР имеют `Expires` в году 3025**, отсекать порогом 2100.
8. **`LocationId` в потоке — int**, не строка.
9. **`time-scale=1` в истории AODP отстаёт**, использовать `24`.
10. **ЧР не покупает снаряжение собирателя и рюкзаки** (`buy = 0`, нулевая
    история). Сумки и фракционные плащи — покупает.
11. **Мой прошлый диагноз «теряется половина ордеров» был НЕВЕРЕН.** Это был
    двойной счёт тем. Урок: прежде чем объявлять потерю данных, проверить, нет ли
    наоборот дублирования.

### 13.2 Арифметика и отображение

12. **Множители округлять до 6 знаков.** `1 − 0.04 − 0.025 = 0.9349999999999999`
    против `0.935` на экране — переворачивает округление.
13. **Все производные значения должны воспроизводиться из показанных чисел.**
    Иначе пользователь с калькулятором «поймает» инструмент на вранье.
14. **Сортировать по точному `rank_exact`, отображать округлённый `rank_score`.**
    По округлённому — ~20 строк на балл, порядок случайный, список «прыгает».
15. **Перцентильное ранжирование, не min-max.** Распределения скошены; min-max
    схлопывает всё, кроме выброса, в ~0.
16. **Качества показывать названиями, не `q1..q5`.** Пользователь не мог
    сопоставить с игрой. `q3` → «Выдающееся» (переименовано по его просьбе с
    «Незаурядное»).

### 13.3 Логика

17. **Планировщик бюджета должен ставить сколько влезает по бюджету, а не долю.**
    Был баг: на бюджет 10 млн выдавалось только на 2 млн.
18. **Валидировать `buy_city`.** Без валидации произвольный город молча давал
    пустой результат вместо `400`.
19. **Эквивалент по силе требует совпадения ИМЕНИ, не только семейства ID.**
    Восемь семейств содержат именные артефакты (`2H_AXE` → «Рука Кхора» и др.) —
    без проверки имени система подменяла обычное оружие артефактом.
20. **Эквивалент не применять к еде, зельям, маунтам.** Зачарованная еда не
    равносильна обычной.
21. **Полнота сета важнее цены.** Город без одной вещи = вторая поездка.
22. **Не терять клик по заголовку во время загрузки.** Был баг: клик в момент
    запроса игнорировался.
23. **Выбросы понижать в надёжности, а не удалять из выдачи.** Удаление скрывает
    информацию от пользователя.
24. **Глубину уценивать по возрасту, а не расширять окно без уценки.** Иначе
    возвращается переоценка доступного количества.

### 13.4 Инфраструктура

25. **Порядок инициализации БД: таблицы → миграции → индексы.** Индекс по
    отсутствующей колонке обрывает апгрейд.
26. **Менять смысл производных таблиц → повышать `DATA_EPOCH`.** Иначе смесь
    старых неверных и новых верных чисел.
27. **Uvicorn — один воркер.** Иначе N планировщиков и N потребителей NATS.
28. **Агрегация в SQL, не в Python.** 887k строк × 6 городов в памяти = OOM.
29. **`git checkout -B`, не `git pull`.** `pull` на ветке фичи отвечает «Already
    up to date», сборка выходит `CACHED`, работает старый код. Полдня поиска
    несуществующего бага.
30. **Всегда заканчивать ответ командой обновления с проверкой версии.** Записано
    в `.kiro/steering/deploy.md`.
31. **Скрипты обслуживания должны быть в образе.** Забыли `COPY scripts/` —
    выдали пользователю неработающую команду. Проверять команды в собранном
    образе, прежде чем отдавать.
32. **Один контейнер на порт.** Проблема «двух сайтов одновременно» — §2.4.

### 14.2 Отвергнутые решения (и почему)

Чтобы не предлагать их заново:

| Предлагалось | Почему отвергнуто |
|---|---|
| Держать агрегацию в памяти Python | 887k строк × 6 городов = OOM |
| Min-max нормализация для ранжирования | выбросы схлопывают остальное в 0 |
| Сортировка по округлённому баллу | ~20 строк на балл, случайный порядок |
| Считать производные из округлённых экранных величин | оценку нельзя воспроизвести |
| Эквивалент только по семейству ID | подменял артефакты |
| Эквивалент для еды/зелий/маунтов | зачарованная еда лучше, а не равносильна |
| Предзагрузка цен на все 8114 предметов каталога сетов | лишняя нагрузка без пользы |
| Широкое окно стакана без уценки по возрасту | переоценка доступного количества |
| `--workers > 1` | N планировщиков и N потребителей NATS |
| Добавить Brecilien как город закупки | слишком далеко/неудобный выход |
| Включить T2–T3 | пользователь прямо отказался |

### 14.3 Что можно сделать дальше

По убыванию пользы:

1. **Обратный груз из Карлеона** (§8.5). Требует: парсинг веса из
   `ao-bin-dumps`, расширение каталога ресурсами и расходниками, модель
   грузоподъёмности. Без веса рекомендация нереализуема.
2. **Мержить PR #3.** Ветка `feat/v5-audit-and-rebuild` содержит всё от 5.0.0 до
   5.3.0. Пока не смержено, команда обновления должна брать ветку (§2.2).
3. **Учёт грузоподъёмности и в прямом рейсе** — сейчас план ограничен деньгами и
   глубиной рынка, но не весом. Для крупных бюджетов это уже ограничивает.
4. **История ставок ЧР по времени суток.** Ставки ЧР зависят от активности
   игроков; знание «когда лучше продавать» дало бы дополнительный процент.
5. **Уведомления по резкому росту ставки ЧР** на отслеживаемые позиции.
6. **Расширить `audit.py`** на вкладку сетов — сейчас он покрывает флипы/план,
   но не логику эквивалентов.

### 14.4 Как общаться с этим пользователем

- **Язык — русский.** Идентификаторы, пути и код — как есть, по-английски.
- **Заканчивать каждый ответ, где менялся код, командой обновления из GitHub**

  «Всегда пиши как обновлять из гитхаба».

  выборочную, и прямо разрешает тратить на это время и токены.
