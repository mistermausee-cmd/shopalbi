# shopalbi — полная инструкция и передаточная документация

Этот документ — исчерпывающий контекст по проекту: что это, как устроено, на чём
работает, какие формулы, всё про игру/рынки/ID Albion Online, и что именно было
сделано в каждом обновлении. Читается как «онбординг за один заход».

---

## 1. Что это

Веб-инструмент для торговли в **Albion Online** (сервер **Europe**, аккаунт с
**Premium**). Собирает цены со всех королевских городов и Чёрного рынка Карлеона,
считает среднее/объёмы за периоды и находит самые выгодные вещи для схемы
**«купил в городе → отвёз в Карлеон → продал на Чёрный рынок»**.

Игру запускать НЕ нужно. Все данные берутся из публичных источников проекта
**Albion Online Data Project (AODP)**. Sandbox Interactive (разработчик игры)
официально разрешает **смотреть и анализировать** рыночные данные; запрещено
модифицировать/вмешиваться в игру или сервисы. Никакой автоматизации игрового
персонажа в проекте нет и не будет — только чтение данных.

Вкладки интерфейса:
- **🔥 Выгодные флипы** — топ вещей на вывоз в ЧР (прибыль в серебре и %, скорость выкупа, надёжность).
- **💡 Рекомендации к покупке** — оптимизатор бюджета: даёт город + список вещей и количество под твой бюджет.
- **🏙 Топ городов** — где выгоднее всего закупаться по совокупности факторов.
- **📊 Средние цены** — таблица средневзвешенных цен и оборота по всем городам за день/3д/неделю/месяц.

## 2. Технологии

- **Backend:** Python 3.12, FastAPI, Uvicorn. Хранилище — SQLite (stdlib, WAL).
- **Планировщик:** APScheduler (фоновые обновления).
- **HTTP-клиент к REST:** `requests` (пейсинг под лимит, gzip, ретраи).
- **Живой поток:** `nats-py` (подписка на публичный NATS-фид AODP).
- **Frontend:** статический SPA — vanilla JS + CSS (без сборки), тёмная тема, русский. Отдаётся самим FastAPI.
- **Деплой:** Docker + docker-compose, один контейнер, том для данных, бинд-маунт логов в `/root/logs`. Запуск: `docker compose up -d --build`.
- **Требования к VPS:** 1 vCPU / 1 ГБ (Azure B1s), без GPU. Ubuntu 24.04.

## 4. Источники данных (на чём всё работает)

### 4.1 REST API AODP
- Хосты по регионам: `https://europe.albion-online-data.com` (EU, наш),
  `west...` (Америка), `east...` (Азия).
- **Текущие цены:** `/api/v2/stats/prices/{item_ids}.json?locations=...&qualities=1,2,3,4,5`
  - поля на (item, city, quality): `sell_price_min` (по чём КУПИТЬ — нижний ордер продажи),
    `sell_price_max`, `buy_price_min`, `buy_price_max` (по чём у тебя ВЫКУПЯТ — верхний ордер покупки),
    и даты каждого (`*_date`) для оценки свежести.
  - **Важно:** REST отдаёт только ОДНУ лучшую цену. Глубины стакана (сколько штук по каким ценам) в REST НЕТ.
- **История:** `/api/v2/stats/history/{item_ids}.json?date=MM-DD-YYYY&end_date=...&locations=...&qualities=...&time-scale=24`
  - `time-scale`: 1=час, 6=6ч, 24=день. Мы берём 24.
  - поля на день: `item_count` (сколько штук продано), `avg_price`, `timestamp`.
- **Золото:** `/api/v2/stats/gold.json` (не используется сейчас).
- **Лимиты:** 180 запросов/мин, 300/5мин. Длина URL ≤ 4096 символов. Просят gzip. Мы держим ~170/мин и батчим ID под лимит длины.
- Числовые location ID REST тоже принимает и возвращает имя города в поле `city` (этим я подтвердил карту локаций).

### 4.2 Каталог предметов
- `ao-bin-dumps` (репо `ao-data/ao-bin-dumps`), файл `formatted/items.json` (~24 МБ, ~12071 запись).
- Формат записи: `{"UniqueName":"T4_BAG@2","LocalizedNames":{"EN-US":"...","RU-RU":"..."}}`.
- Зачарованные варианты идут ОТДЕЛЬНЫМИ записями (`@1..@4`), поэтому просто фильтруются, а не генерируются.
- Локации: `formatted/world.json` (id ↔ имя зоны/здания).

### 4.3 Живой поток (NATS) — глубина стакана
- Публичный фид AODP, подключается прямо с VPS (исходящее TCP, клиент Альбиона НЕ нужен):
  - EU: `nats://public:thenewalbiondata@nats.albion-online-data.com:34222`
  - US: `:4222`, Asia: `:24222`
- Топики: `marketorders.deduped` (ордера без дублей — используем его), `marketorders.ingest` (с дублями),
  `markethistories.*`, `goldprices.*`.
- **Каждое сообщение = один рыночный ордер** со структурой (`albiondata-client/lib/market.go`):
  ```
  Id, ItemTypeId (напр. T5_OFF_TORCH@1), ItemGroupTypeId, LocationId (число),
  QualityLevel, EnchantmentLevel, UnitPriceSilver, Amount (КОЛИЧЕСТВО!),
  AuctionType ("offer"=продажа | "request"=покупка), Expires (ISO)
  ```
- Именно здесь есть **глубина**: цена + количество на каждый ордер. REST этого не даёт.
- Проверено вживую: ~3 ордера/сек по EU (~250k/день). За 45 c реально пришло 180 ордеров экипировки.
- Оговорка (шифрование, янв. 2024): у части аккаунтов рыночные данные зашифрованы, с них live-ордера не читаются (история/золото — читаются). Публичный фид сглаживает: собирает со всех, у кого не зашифровано.

### 4.4 Дампы БД
- `albion-online-data.com/database-europe/` — ежедневные бэкапы БД и помесячная `market_history` (агрегат). Для live-глубины не годятся; глубина только в потоке. Сейчас не используются.

## 5. Игровые знания (важно для математики)

### 5.1 Тиры и зачарование
- Тиры T1–T8. Мы сканируем **T4–T8** (боевая экипировка).
- Зачарование `.0`–`.4`. В ID предмета кодируется суффиксом `@1..@4` (`.0` = без суффикса).
- В интерфейсе показываем слитно: **`Т4.1`** = тир 4, зачарование 1 (кириллическая «Т»).
- RU-названия тиров (в скобках у предметов в дампе): T4 Знаток, T5 Эксперт, T6 Мастер, T7 Магистр, T8 Старейшина. Мы это слово-тир из имени ВЫРЕЗАЕМ (дублирует бейдж «Т4.1»).

### 5.2 Качество (отдельная ось!)
1 Обычное · 2 Хорошее · 3 Незаурядное · 4 Отличное · 5 Шедевральное. К зачарованию отношения не имеет.

### 5.3 Города
- Королевские: Bridgewatch, Fort Sterling, Lymhurst, Martlock, Thetford, Caerleon, Brecilien.
- **Brecilien исключён из закупок** (далеко, тяжело выйти в Карлеон). Остаётся в таблице средних цен для справки, но не в флипах/рекомендациях/рейтинге. Список городов-источников = `BUY_CITIES` = все royal минус Brecilien.

### 5.4 Чёрный рынок (ЧР)
- Только в Карлеоне. Управляется игрой: генерирует **ордера покупки** (buy orders) под спрос лута. Игрок только ПРОДАЁТ в них.
- Покупает **только боевую экипировку**: оружие, оффхенды, броня (шлем/нагрудник/обувь), плащи, сумки. НЕ покупает ресурсы, рефайн, еду, зелья, маунтов, инструменты.
- Проданные ЧР вещи потом выпадают как лут у мобов/в сундуках.

### 5.5 Налоги (у нас Premium)
- **Налог с продажи** (при завершении сделки): 4% с Premium, 8% без.
- **Сбор за размещение** (setup fee): 2.5% от стоимости лота, при выставлении ордера.
- Модель: чистая выручка = цена × (1 − 0.04 − 0.025) = **× 0.935**. Покупка из существующего ордера продажи — без сбора.
- Всё настраивается: `SHOPALBI_SALES_TAX`, `SHOPALBI_SETUP_FEE`.

### 5.6 Числовые Location ID (карта фида/REST) — ПРОВЕРЕНО
```
7    -> Thetford
1002 -> Lymhurst
2004 -> Bridgewatch
3003 -> Caerleon         (обычный рынок; в фиде offer-доминантный)
3005 -> Black Market     (Чёрный рынок; NPC buy-ордера)
3008 -> Martlock
4002 -> Fort Sterling
5003 -> Brecilien
```
Как подтвердил: запросил REST `locations=3003,3005,3008,2004,1002,4002,7,5003` — вернулись имена
[Caerleon/Black Market + остальные шесть]. Известные шесть закрыли шесть имён; оставались `3003`/`3005`
на `Caerleon`/`Black Market`. По живому фиду `3003` — offer-доминантный (обычный рынок, где игроки
выставляют продажи) → это Caerleon; значит `3005` = Black Market. (Примечание: в `world.json` игры
`3005`=«Caerleon Market», `3003`=«Caerleon» — у AODP своя разметка, она главнее для наших данных.)

### 5.7 Паттерн ID предметов и фильтр экипировки ЧР
- ID: `T{tier}_{SLOT}_...` (+ опц. `@enchant`). Токены слота:
  - `MAIN`, `2H` → оружие (weapon)
  - `OFF` → оффхенд (offhand)
  - `HEAD`, `ARMOR`, `SHOES` → броня (armor)
  - `CAPE`, `CAPEITEM` → плащ (cape)
  - `BAG` → сумка (bag)
- Исключаем: `_TOOL` (инструменты сбора), `NONTRADABLE`.
- Итог фильтра: ~**6852** предмета экипировки T4–T8 (со всеми зачарованиями), с RU-именами.

## 6. Формулы (ядро — `engine.py`)

Обозначим `net = 1 − SALES_TAX − SETUP_FEE = 0.935`.

### 6.1 Прибыль флипа (по REST, одна цена)
```
Затраты  = sell_price_min (город)           # покупка из ордера продажи, без сбора
Выручка  = buy_price_max (ЧР) × net          # продажа в buy-ордер ЧР, минус налог+сбор
Прибыль  = Выручка − Затраты
Прибыль% = Прибыль / Затраты × 100
```

### 6.2 Средневзвешенная цена за окно (для вкладки цен и опорной недельной)
```
VWAP = Σ(avg_price_i × item_count_i) / Σ(item_count_i)     # по дням окна из history
объём_день = Σ(item_count_i) / дней_в_окне
```
Окна (дней): день=1, 3д=3, неделя=7, месяц=30.

### 6.3 Скорость выкупа ЧР (оценка)
```
время_выкупа_1_шт ≈ 24 ч / объём_день(ЧР)
```
Честно помечается как оценка (игра точное «время» не отдаёт).

### 6.4 Надёжность флипа (0..100)
```
fresh     = clamp(1 − max(возраст_покупки, возраст_ЧР) / FLIP_MAX_AGE_HOURS)   # свежесть цен
liquidity = clamp(объём_день_ЧР / 20)                                          # ликвидность
stability = clamp(прибыль_по_недельной / прибыль_текущая)   если тек.>0 иначе 0 # не разовый ли скачок
score     = round(100 × (0.40·fresh + 0.30·liquidity + 0.30·stability))
```
Так надёжный ликвидный флип получает 65–85, а фантомный скачок без объёма — 8–25.

### 6.5 «Выгодность» (композит по совокупности факторов) — сортировка флипов по умолчанию
```
opportunity = round(прибыль_текущая × score / 100)     # ожидаемая реализуемая прибыль
```

### 6.6 Рейтинг городов
Для каждого города суммируем `opportunity` его лучших 100 флипов → `score` города. Сортируем по убыванию.
Плюс кол-во флипов, суммарная прибыль топ-100, средний %, средняя надёжность, лучший предмет.

### 6.7 Рекомендатель по РЕАЛЬНОЙ глубине (главная фича) — `_plan_city` / `_greedy_fill`
Есть живой стакан (из NATS): для (item, quality) в городе — список офферов продажи, у ЧР — список buy-ордеров.
```
offers = ордера продажи города, по возрастанию цены
reqs   = buy-ордера ЧР, по убыванию цены
Двухуказательное сведение:
  buy = offers[i].price; sell = reqs[j].price
  margin = sell × net − buy
  если margin ≤ 0: стоп (дешёвый оффер больше не бьёт лучший выкуп ЧР)
  lot = min(offers[i].amount, reqs[j].amount)   # ограничено РЕАЛЬНЫМИ количествами
  фиксируем "fill": (item, buy, sell, lot, unit_profit=margin)
  вычитаем lot из обоих; двигаем исчерпанный указатель
```
Все fills со всех предметов города → **жадное распределение бюджета**:
```
сортируем fills по эффективности (unit_profit / buy) по убыванию
идём по списку: qty = min(fill.qty, остаток_бюджета // buy); покупаем; вычитаем из бюджета
агрегируем по предмету: кол-во, средняя цена = Σстоимость/Σкол-во, прибыль = Σ(unit_profit×qty)
```
Ключ: количество к покупке **никогда не превышает реальные объёмы стакана** (и спрос ЧР, и предложение города) — поэтому фантомных «купи 200 шт T4» больше нет.

### 6.8 Фолбэк-оценка, когда живой глубины ещё нет — `_estimate_plan`
Пока стакан пуст (прогрев/тонкий фид): считаем по REST (одна цена), количество на предмет жёстко ограничено `RECOMMEND_NODEPTH_CAP` (по умолчанию 10). Есть также модель роста цены при скупке (slippage) для старой логики, но основной путь теперь — реальная глубина. Позиции помечаются тегом `оценка` (иначе `live`).

## 7. Модель данных (SQLite, `storage.py`)

- **items**(item_id PK, base_id, tier, enchant, slot, category, name_ru, name_en) — каталог экипировки ЧР.
- **current_prices**(item_id, city, quality, sell_price_min, sell_price_min_date, buy_price_max, buy_price_max_date, fetched_at) PK(item_id,city,quality) — снапшот REST.
- **history**(item_id, city, quality, day, item_count, avg_price) PK(...,day) — дневная история (31 день).
- **order_book**(order_id PK, item_id, city, quality, side, price, amount, expires, seen_at) — ЖИВОЙ стакан из NATS. side = 'offer'|'request'. Протухшие (по `expires` или старше `ORDER_MAX_AGE_MINUTES`) периодически удаляются.
- **meta**(key, value) — таймстемпы обновлений, счётчики.

PRAGMA: WAL + synchronous=NORMAL (конкурентное чтение при записи).

## 8. HTTP API (`main.py`)

- `GET /api/status` — таймстемпы обновлений, кол-во предметов, размер стакана, налоги, окна.
- `GET /api/meta` — справочники: города, buy_cities, качества, тиры, категории, окна, налог.
- `GET /api/stats?window=&category=&tier=&quality=&search=&sort=&direction=&limit=&offset=` — таблица средних цен по городам (сортировка по любой колонке, включая `city:<Город>`).
- `GET /api/flips?window=&min_profit=&min_bm_volume=&category=&tier=&quality=&search=&buy_city=&sort=&direction=&limit=` — флипы. sort: opportunity(деф.), profit, profit_pct, reliability, bm_volume, buy_price, bm_buy_now, est, buy_city, name, tier.
- `GET /api/cities?window=&...&top_n=` — рейтинг городов.
- `GET /api/recommend?budget=&city=&window=&min_profit=&min_bm_volume=&category=&tier=&quality=&search=` — оптимизатор бюджета (город авто/фикс, список покупок). Ответ: best (план) + cities (сравнение) + has_depth + orderbook_orders.
- `POST /api/refresh` — запустить фоновое обновление REST-данных.
- `GET /api/health` — проверка живости (для healthcheck).
- `GET /` и статика — фронтенд.
- Опциональный HTTP Basic (`SHOPALBI_AUTH_USER/PASS`, по умолчанию выключен).

## 10. Запуск, деплой, отладка

**Один раз (Ubuntu 24.04):**
```bash
curl -fsSL https://get.docker.com | sudo sh
git clone https://github.com/mistermausee-cmd/shopalbi.git && cd shopalbi
sudo docker compose up -d --build
```
Открыть `http://IP_VPS:8000`. В Azure открыть порт 8000 в NSG.

**Обновление:**
```bash
cd ~/shopalbi && git pull && sudo docker compose up -d --build
# затем в браузере Ctrl+F5 (иначе кэшируется старый app.js)
```

**Логи:** `sudo docker compose logs -f`, файл — `/root/logs/shopalbi.log` (бинд-маунт на хост).

**Локальный прогон/тесты (Python 3.12, ВАЖНО — не 3.9):** венв на 3.12, `pip install -r requirements.txt`,
тесты гонял через `fastapi.testclient.TestClient` (без реального порта) и прямыми вызовами `Analytics`.
Живой NATS проверял отдельным скриптом: `NatsConsumer(storage).start()` + sleep + `order_book_count`.

- venv по умолчанию мог собраться на Python 3.9 → FastAPI не переваривает `X | None` в сигнатурах эндпоинтов. Нужен 3.10+ (Docker = 3.12).
- CSS: класс с `display:flex` перебивал HTML-атрибут `hidden` → добавлено `[hidden]{display:none!important}`.
- `git pull` писал «Already up to date», если рабочая копия была не на `main` — деплой брал старый код и Docker кэшировал `COPY`. Лечение: `git checkout -B main origin/main` + `--build`.
- `/tmp` в песочнице очищается между вызовами — тесты гонять одной командой.

## 13. Ключевые оговорки (честно)

- Данные краудсорсные: в потоке/REST только те рынки, что игроки открывали в игре. Пустые рынки не появятся.
- «Скорость выкупа» и прогнозы — оценки по историческому обороту, не гарантия.
- Прибыль считается на мгновенную продажу в существующий buy-ордер ЧР (налог+сбор 6.5% с Premium).
- Шифрование части аккаунтов (SBI) может резать live-ордера у отдельных игроков; публичный фид это сглаживает.
- Тег `live` = расчёт по реальному стакану; `оценка` = глубины по предмету пока нет, количество ограничено сверху.
